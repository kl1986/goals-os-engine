# A Project declares its repos; a Ticket does not

Nothing in Goals OS linked a Project to a codebase — neither ADR-0015's ticket frontmatter nor `project-tracking.md`'s Project schema — so `/build` had no way to know where a Ticket's code lands. The Project note gains a **`repos:` list**, holding paths relative to a new **`code_root`** setting in the Brain's `config/`; Tickets gain nothing. A Ticket's owning folder (`tasks/projects/<slug>/`) already identifies its Project, so Project-level declaration is sufficient, and where a Project names more than one repo the Foreman resolves per Ticket at Phase 0 and states the mapping for confirmation before spending anything. Decided 23/07/2026.

**Considered options.** *`repo:` on ticket frontmatter* — maximally explicit and needs no resolution step, but requires a retrofit across every existing ticket and adds a field that is blank and meaningless on the 16 of 18 Projects that have no code at all. *Pure slug convention (`<code_root>/<project-slug>/`)* — declares nothing, but the convention does not hold in reality (slug `goals-os` → folder `Goals OS`; slug `epoch-fit-mvp` → folder `Epoch Fit`) and cannot express that one Project means three git repos (`goals-os-engine`, `goals-os-library`, `goals-os-brain`); any fix for that is a declaration in disguise. *Absolute paths* — works immediately, but hardcodes one machine into a schema meant to ship. *git remote URLs* — most portable, but adds a resolve-or-clone step every run and is incoherent for the Brain repo, which the agent is already running inside.

**Consequences.** `repos:` being absent is load-bearing, not an omission: it is what makes pointing `/build` at a non-code Project (`organise-kats-40th`, a Work-area ticket) fail closed as a Readiness quarantine, with no separate guardrail needed. `code_root` is per-Brain user state, so it lives in the Brain per ADR-0003 and never in the Engine or Library.
