# The Build pipeline is sized per ticket, in two stages, and only ever upward

A Build selects one of three **pipeline shapes** — Light, Standard, Full — which differ only in which Reviewer passes are commissioned (correctness / +integration / +adversarial) and how many dispute rounds are allowed (1 / 2 / 3). The Surveyor and the Coder are identical in every shape and no shape drops review. The shape is selected twice: a **provisional** shape declared in the pre-spend Batch echo, and a **binding** shape measured from the Coder's actual diff before the Reviewer is commissioned. Selection is upgrade-only in both directions of travel — a narrower diff never lowers a heavier prediction, and a failing Reviewer round raises the shape rather than escalating. Decided 28/07/2026.

**Why:** `/build` ran the heavy configuration regardless of the work — Surveyor, Coder, Reviewer, three dispute rounds — applied to a single-repo, single-file, fully-specified ticket exactly as to a cross-cutting one. The 28/07/2026 Build of [[triage-plan-approval-is-not-tappable-in-obsidian-mobile]], one repo and one ticket, spent ~2.24M sub-agent tokens; the Antigravity-side orchestrator already carries a cautionary figure of ~437K for the same mistake, and the Claude Code Adapter carried no equivalent sizing rule at all.

This is emphatically **not** a decision to review less. On that same Build the Reviewer found five real defects, two of which would otherwise have shipped: a converter that silently deleted Triage Rows along with their approval state, and a capture-controlled injection letting any email sender plant a phantom approval checkbox in a Plan — a Principle 10 violation. A Build touching the parser that Execute, the nudge and the Dashboard all share is exactly where the full loop belongs, and it earned its cost there. What was missing was not review but **choice**: the shape was never selected, never declared, and never justified, so it could be neither defended nor overridden.

**Blast radius is the signal, not ticket size or diff size.** A shared parser or a destructive one-off migration warrants the full loop however small its diff; a contained single-file change with no dependents does not become dangerous by being long. Both defects above were blast-radius defects, and both are caught by passes the lighter shapes do not run.

**Why two stages.** Blast radius is a property of the files a Build changes, and those files do not exist when the Batch is echoed. A single pre-spend decision would therefore have to be a guess dressed as a commitment. The resolution is that the expensive commission — the Reviewer — runs *after* the diff exists, so the guess need only be honest, not accurate: stage 1 predicts from what is genuinely knowable pre-diff (how many repos the Project declares, whether the ticket is Hardened, any candidate files the Surveyor named) and is **labelled a prediction**; stage 2 measures the real changed files (migrations and converters, destructive operations, capture-controlled input, non-test source and test module counts, whether anything else references a changed file) and is what the Reviewer is actually commissioned under.

**Quarantine on ambiguity, extended to sizing.** An unmeasurable signal — an unwalkable repo, a file that will not read as text, no diff at all — selects Full. Ambiguity selects the heavier shape, never the lighter one, exactly as an unanswered Survey prompt selects quarantine rather than proceeding on assumptions.

**A failing round ratchets rather than escalates.** A defect found under a light shape is evidence the Build was sized too optimistically, so the shape rises (Light → Standard → Full), adding both a pass and a round. Escalation to the user happens only when Full exhausts its rounds. The cap is **cumulative, never re-granted**, so no Build exceeds the pre-existing three-round ceiling of ADR-0023 — right-sizing can cost less than the old fixed configuration and never more.

**Binding in code, not in charter prose.** The 28/07/2026 Build ran six Reviewer rounds against a documented cap of three, because the cap lived only in prose that an LLM Foreman was free to not follow. So `run_dispute_loop` takes the shape as a **required argument with no default cap**, the Reviewer's brief is **generated** from the shape rather than composed by the Foreman, and the echo and the Action Log entry render from the same object. This does not make an unshaped Build impossible — nothing stops a Foreman commissioning a Reviewer directly — but it makes that path conspicuously missing its echo, its brief and its log record instead of silent.

**Trade accepted:** the pre-spend echo is a prediction, so a Build announced as Light may end up paying for Full, either because the diff turned out wider than predicted or because a round found a defect. Kelvin sees a shape change mid-run rather than a number he was promised. That is the honest ordering — the alternative is a confident pre-spend number that is wrong more often and cannot be corrected by evidence. A second accepted cost: with stage-1 structural signals deliberately excluded (see below), nearly every hardened single-repo ticket echoes as provisionally Light, which makes the pre-spend echo weakly informative; it is retained because it is the override point, not because it is a good predictor.

**Rejected:** a **declared blast-radius registry** keyed on `component:` — deterministic and auditable, but it requires a human curator, and the only available curator is the one person in the system who is explicitly not an engineer; a registry nobody maintains is a registry that lies, and mis-declaring a component would become a way to buy a cheap review. **Absolute fan-in thresholds** — they do not transfer between repos (the library's busiest module has a fan-in of 3, the engine's has 18), so any constant would be tuned to one repo and meaningless in the other; the reverse-dependency check therefore asks only the binary question of whether anything else depends on a changed file. **A keyword scan of the ticket body at stage 1** — a ticket that happens not to use the word "migration" would buy itself a cheap review, and a scan that can only raise the shape adds little over measuring the diff properly at stage 2. **A special case forcing Full whenever the sizing code itself is touched** — correct in spirit, since a defect there silently downgrades every future Build, but special cases accumulate and the rule set is more valuable uniform; the consequence, accepted knowingly, is that a change to the sizing code scores Light on its own signals. **A hard pin that survives stage 2** — an override that stage 2 must respect would let a stated preference beat measured evidence about a migration; the override sets the starting shape instead, and a true pin can be filed as a follow-up if it is ever actually wanted. **Removing the Reviewer or the dispute loop from the heavy shape** — never on the table; the 28/07 Build is the standing argument against it.
