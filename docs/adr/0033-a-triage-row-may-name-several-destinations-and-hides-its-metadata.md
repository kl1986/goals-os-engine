# A Triage Row may name several destinations, and hides its classification metadata

A Row's destination field accepts a **comma-separated list** of backticked destinations — one capture, filed to each in turn — and the `route · confidence · rule` triple is wrapped in `%%…%%`, an Obsidian comment, so it is present on the line but invisible in reading view. Decided 31/07/2026. Extends ADR-0031; does not replace it.

**Why:** Triaging email, Kelvin's judgement was that the reading surface asks him to parse things he never uses and refuses to record the thing he actually wants to say. On the 23/07 email plan, 25 of 32 rows were noise and every surviving row could only go to one place. Two separate complaints, one line:

*"I don't know what the point of the Pass B, the dots and the dashes is for, it certainly doesn't add anything to me when I'm in triage mode. If it's not noise then I think it needs options for action yes or no and then whether it goes to area, project and/or wiki."*

The metadata is not useless — `rule` is what lets rule-learning group corrections against the specific rule that fired, and `route`/`confidence` are read by the Action Log. It is useless **to the human doing the approving**, which is the one thing the Row line exists for. So the fix is to hide it, not to move or drop it. Wrapping in `%%…%%` keeps every field exactly where `ROW_RE` already expects it, which preserves ADR-0031's load-bearing property: parsing stays **line-local**, one line remains independently meaningful, and `triage_pending.py` and `dashboard.py` keep reading Rows with no knowledge of layout. Relocating the triple to a continuation line would have bought the same visual result at the cost of that property, and of the continuation arity that makes a Row block unambiguous.

The list is the other half. A capture that belongs in both an Area and a Project genuinely has two destinations, and the single-destination field forced a choice that discarded real information — the same shape of loss as [[allow-discard-as-a-pass-a-routing-rule-destination]], where the only expressible rule for LinkedIn alerts was the wrong one. `destination` remains as a key on the Row dict, holding the first entry, so every existing consumer and every Row written before this decision is unaffected.

**One Row is still one action.** The multi-destination path writes to each destination in turn but archives the capture **once**, calls the per-source `execute_hook.py` **once**, and writes **one** Action Log entry whose `outcome` names every destination. This is deliberate: the Row is one human gesture, and the audit trail should be 1:1 with the gesture rather than with the file writes. N entries for one tick would also inflate the graduation engine's counting and give rule-learning N copies of a single decision to group.

**Two combinations are refused outright**, before any side effect, joining the blank destination ADR-0031 already refused:

- **`discard` alongside a real destination** — "file nowhere" and "file here" are contradictory, and unlike a blank it looks deliberate, so acting on either half would be guessing at which the user meant.
- **the same destination twice** — one capture filed to one place twice duplicates the entry, and no reading of the Row wants that.

Both are whole-Plan refusals rather than per-row errors, for ADR-0031's reason: a half-executed Plan whose remaining rows are ambiguous is strictly worse than an untouched one.

**Trade accepted:** a partial write is now possible where it was not before. If the second destination of a two-destination Row raises mid-run, the first has already been written. The Row is reported as an error, its capture is *not* archived and its tick is *not* stamped, so a re-run after the fix completes it — but the first destination will then hold the entry twice. Detecting that would mean either a transaction across arbitrary markdown files or a read-back-and-compare before every write, both of which cost more than the failure is worth: `_file_capture` raises only on a destination that does not exist, which the refusal pass and the duplicate check already catch for every case except a directory deleted mid-run.

**Trade accepted:** an already-open Plan keeps its metadata visible until Triage next writes to it. Execute's write path moves Row blocks verbatim and appends the executed marker; making it also normalise punctuation would put every Row's tick and marker state through a reformat for a cosmetic gain. The `%%` is therefore optional on read, and new Plans are wrapped from their first write.

**Rejected:** *moving route/confidence/rule to a continuation line* — same visual result, but it breaks line-locality and the continuation arity, the two things ADR-0031 spent its length protecting; *dropping the metadata from the Row entirely and keeping it in a sidecar* — the Action Log and rule-learning both need it per-Row, and a sidecar keyed by row number is a second thing to keep in sync with a file the user hand-edits; *a second grammar for multi-destination Rows* — ADR-0031 rejected dual-shape parsing for the table conversion and the reason holds, so this is one field generalised, read by the same regex, not a second shape; *N Action Log entries for N destinations* — see above; *making `discard` + a real destination mean "file it, then bin the raw"* — a coherent reading, but it is not what anyone typing it means, and inferring intent from a contradiction is exactly what the refusal exists to prevent.
