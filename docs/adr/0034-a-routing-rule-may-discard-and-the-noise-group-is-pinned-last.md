# A routing rule may discard, and the noise group is pinned last

`config/routing-rules.md` accepts `then: discard` alongside `then: route -> <path>`, so Pass A can classify a capture as noise. In a Triage Plan the `discard` group is ordered **after every other group**, whatever its Rows' document positions. Decided 31/07/2026.

**Why:** Discards are the bulk of triage and the part that least deserves attention — 25 of the 32 Rows on the 23/07 email Plan, 9 of 12 on the 28/07 one. Until now the rule format could only name a file destination, so the single most repetitive judgement in the Brain ("this sender is noise") was the one thing Pass A could not express. Every discard was a model decision, in-session, and every one was due to recur for the same sender the next morning.

The 27/07 bootstrap batch shows the cost precisely. It proposed `jobalerts-noreply@linkedin.com → areas/work/_inbox.md`; Kelvin rejected it, correctly — he bins LinkedIn job alerts, he does not file them to Work. But the only *expressible* rule for that sender was the wrong one, and `rule_diff_review.diff_key()` de-dups against archived rejections, so the sender became permanently un-proposable. Nine of the 32 Rows on 23/07 were that sender. That is the generic outcome whenever the right answer is "discard": the format forces the proposer to name a file or say nothing.

`then: discard` parses to the destination literal `discard`, which Execute already understands (`action_type_for`), so a Pass A discard and a Pass B discard are the same Row downstream and nothing in Execute changes. `then: route -> discard` hashes to the same rule id: same parsed destination, same behaviour, one rule written two ways, and the id answers "which rule fired".

**Pinning the noise group last** is what turns this into a usable page rather than just a cheaper classification. Grouping is by destination (ADR-0031), so with `then: discard` in play the Plan naturally acquires a large noise group — but it forms wherever its first Row happens to sit, which for an email sweep is usually Row 1, putting the part needing no attention at the top. Pinned last, the Rows wanting a decision are what you land on, and Obsidian's native heading fold collapses the rest out of sight.

Heading folding is deliberately the collapse mechanism. The obvious alternative — a `> [!info]-` callout — cannot hold Rows at all: a callout's lines begin `> `, and `ROW_RE` anchors on `^[ \t]*- \[`, so every Row inside one would become invisible to Execute, the nudge and the Dashboard. A plain `##` heading gives the same one-tap collapse with no contract damage.

**This amends ADR-0031's ordering rule**, which said a group's position comes only from the document position of its first Row. It now comes from that *and* whether the group is `discard`. The property that rule existed to protect is intact: group order remains a deterministic function of the Rows alone, stable across passes, so re-grouping is still a fixed point and a heading edit is still inert — renaming `## discard` produces a result identical to not renaming it. What changes is the base ordering, once, for one destination. No open Plan in the Brain held a `discard` group when this landed, so nothing mid-approval was reordered by it.

**Deliberately not done: pre-ticking noise Rows.** "Default to noise" here means *classified* as noise, not *approved* as noise. Every Row still needs an explicit `[x]` before Execute touches it (ADR-0031; `protocols/triage.md`), and pre-ticking would make Triage's write an approval on the user's behalf — auto-execution on confidence, which is Phase 5's graduation and gated on evidence this Brain does not yet have (every one of its Action Log entries still reads `feedback: —`). The gesture cost of ticking a large noise group is real and is the honest price of confirm-first; the group being folded and pinned is the part that can be fixed without touching the safety property.

**Trade accepted:** an over-broad discard rule routes something that mattered into the noise group. Three things contain it — the Row still needs a tick, a discarded capture is archived rather than deleted (`protocols/capture.md`) so it is recoverable from `archive/inbox/`, and rules are additive-only so a bad rule can be superseded but never silently rewrites history. This is nonetheless the first rule class whose *default* outcome is "nothing gets filed", and confirm-first is the only thing between it and silent loss.

**Rejected:** *a `[!info]-` callout for the noise group* — breaks Row parsing outright, see above; *a separate `noise:` section outside the group mechanism* — a second organising principle competing with destination grouping, which ADR-0031 deliberately made the only one; *pre-ticking* — see above; *sorting every group by size rather than pinning one destination* — size is a property of the document that changes as Rows are re-routed, so it would reorder the page mid-approval, exactly the defect ADR-0031's ordering rule exists to prevent.
