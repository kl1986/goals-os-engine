# A Triage Plan offers to make a rule from a repeat sender

An email Triage Plan carries a final section, `## Stop asking me about these`, holding one checkbox per sender that still costs a decision. Ticking one proposes a `then: discard` rule for that sender as a diff in `inbox/rule-diffs/`. Decided 01/08/2026.

**Why:** The same senders recur every morning — 8 LinkedIn Job Alerts in a single 15-row Plan, 6 in another, 2 Well-Man Cars booking mails that are one decision — and until now the only way to stop being asked was to hand-write a rule in `config/routing-rules.md`. That means leaving the page, knowing the file exists, and knowing its syntax. Meanwhile the judgement "this sender is always noise" is one the user is *already making*, on that page, at that moment. This puts it one tap from where the decision actually happens.

It also closes the loop ADR-0034 opened: `then: discard` made noise expressible as a rule, but nothing generated such rules, so `config/routing-rules.md` would only ever grow by hand.

**The checkboxes are deliberately not Rows.** They carry no row number, no destination and no capture wikilink, so `execute.ROW_RE` cannot match them: Execute can neither act on them nor be confused by them, and the nudge and Dashboard do not count them as pending work. They are prose under a heading, which `regroup_plan` already preserves — and which it now ranks last, after `discard`, since the section summarises the noise and should be read after it. Group rank is a property of the destination rather than of the document, so re-grouping remains a fixed point.

**A tick proposes; it does not apply.** The tick is a direct human instruction, and writing the rule straight into `config/routing-rules.md` would be one tap cheaper. It still goes through `inbox/rule-diffs/`, because that surface already owns rule changes and provides four things a direct write would bypass: additive-only application, the de-dup key that stops a rejected rule being re-proposed forever, an Action Log entry, and archival. The cost is a second confirmation; the benefit is that the one mechanism that can silently bin mail has exactly one way in.

**Evidence is the captures, not a relaxed bar.** The review surface requires ≥2 evidence links, having been built for machine-detected correction patterns. Rather than weaken that for human-originated diffs, a proposal carries the sender's own Raw Captures from the Plan as its evidence — a sender recurring often enough to deserve a rule has ≥2 by definition. A sender with only one sighting is refused at the tick, with a reason, rather than written as a diff that fails validation later out of sight. This adds `sender-marked-noise` alongside `bootstrap-raw-captures` as a raw-capture evidence basis: identical validation (do these captures exist?), distinct name so the record says which mechanism produced a rule. The bootstrap's separate "requires an empty routing-rules.md" guard stays bootstrap-only — it exists to stop a seeding pass running twice, and applying it here would make the checkbox work exactly once, on an empty config.

**A sender whose local part varies is matched on its domain.** Some senders randomise it per message (`no-reply-OR7ml8it56ifoQf1S_QVhQ@mail.anthropic.com`), so a rule keyed on the full address would match exactly the capture that produced it and never fire again — a dead rule, re-proposed once per message, cluttering the list it exists to shorten. Where a domain is seen with a single stable local part the full address is kept, since it is the tighter match. Found by running the section against real captures, not by reasoning about it.

**Trade accepted:** the domain collapse can be too broad. `mail.anthropic.com` carries both receipts and security alerts; binning the domain bins both. The containment is unchanged from ADR-0034 — the rule only *classifies*, every Row still needs a tick, and a discarded capture is archived rather than deleted — plus the diff shows the exact rule block before it applies. But this is the first place the system *suggests* a rule broad enough to be wrong, so the suggestion is worth reading rather than reflexively approving.

**Trade accepted:** offered senders are computed per Plan, so a sender appearing once in each of six Plans is offered in none of them. Aggregating across open Plans would catch it, at the cost of a Plan's section describing mail that is not on that page. Per-Plan is the more honest surface; the cross-Plan case is what the weekly rule-learning Routine is for.

**Rejected:** *writing the rule directly on tick* — see above; *offering every sender, including ones already routed by a rule* — the list exists to shrink, so a covered sender must drop out of it, which `is_duplicate()` gives for free against pending, applied and rejected diffs alike; *putting the checkboxes inside the `discard` group* — they would be folded away with the noise, hiding the one control that makes tomorrow's page shorter; *making them Rows so Execute could process them* — Execute files and discards captures, and a rule proposal is neither.
