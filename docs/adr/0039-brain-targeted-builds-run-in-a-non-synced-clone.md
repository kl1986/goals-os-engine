# Brain-targeted builds run in a non-synced clone, never in the iCloud vault

`/build` refuses to create branches or worktrees against any `target_repo` resolving under an iCloud-synced root (`Library/Mobile Documents/iCloud~*`). Brain-targeted builds instead run in a plain clone of `goals-os-brain` held outside iCloud, commit and push from there, and reach the vault through the existing Version control routine's pull. The iCloud vault remains the canonical working copy. Decided 04/08/2026.

**Why:** the live Brain is an iCloud-synced folder, symlinked into `Code/projects/Goals OS/goals-os-brain`. Git worktree mechanics mutate many files at once and rewrite them again on every branch switch; iCloud responds to a write it did not expect to lose by keeping both sides as `"<name> 2.md"`. That is not a hypothetical — the session that raised these tickets cleaned up roughly 198 such conflict copies already accumulated across the vault from ordinary use, before any build had ever run there. Cutting `build/<slug>` branches in that tree would make the same failure a routine by-product of every build, and the duplicates land in a Brain whose content *is* the product.

**Fail-closed, consistent with the plugin's other preflights.** An iCloud-synced target is a halt in the same class as `agy` or the clean-tree check, not a warning. The refusal names the non-synced clone, so the operator is pointed at the fix rather than at the obstacle.

**Why the vault stays canonical.** The obvious tidier alternative — move the git repo out of iCloud and let the vault become a derived working copy — trades one problem for a worse one. iCloud is not incidental here: it is what puts the Brain on Kelvin's phone, and mobile capture and mobile Triage approval are load-bearing (an entire ticket exists because Plan approval had to be made tappable in Obsidian mobile). A build clone is a tool; the vault is where the system is actually used. The tool moves.

**Why not a bare remote as the hub,** which is the orthodox git answer: the remote already exists, and adding a bare repo in front of it introduces a third place where the Brain can be stale without adding a guarantee neither the vault nor the clone already provides. Build → push → the Version control routine's pull is a path that already runs nightly and is already trusted.

**Consequences.** A Brain-targeted build is now asynchronous with respect to the vault: work lands in the clone and appears in the vault on the next pull, so a build's output is not immediately visible where the operator is looking. The clone must be kept current before a build reads from it, or a Coder reasons against a stale Brain. And this decision only removes the *worktree* hazard — the vault tree is still continuously dirty from dashboards, captures, wiki compiles and iCloud itself, which is a separate problem with a separate answer (ADR-0040).

**Rejected:** *refuse and require the operator to pause iCloud sync manually* — puts a manual ritual in front of every Brain ticket and fails open the moment someone forgets; *move the Brain off iCloud entirely* — costs mobile Obsidian sync, which the Brain's own tickets treat as a requirement.
