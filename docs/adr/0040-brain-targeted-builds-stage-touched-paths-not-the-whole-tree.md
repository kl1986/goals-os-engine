# Brain-targeted builds stage the Coder's touched paths, not the whole tree

For a `target_repo` resolving to the Brain, `commit_build_changes` stages exactly the paths the Coder changed — taken from the before/after worktree snapshots the pipeline already captures — instead of `git add -A`. The clean-tree halt is correspondingly narrowed to those paths: a build stops if a file the Coder touched was already dirty, not because unrelated vault activity is in flight. Normal repos keep whole-tree staging and the whole-tree halt unchanged. Decided 04/08/2026.

**Why:** `git add -A` is safe in the build plugin only because of a precondition — a branch is cut from a clean tree, and dirtiness is a halt. For every ordinary repo that holds. For the Brain it is unsatisfiable in principle, not occasionally: dashboards regenerate on a timer, captures land from four sweeps, the wiki compiles, the daily note is written twice a day, and iCloud mutates files continuously. The Brain's steady state *is* dirty. A precondition that is never true does not protect anything; it just means no Brain-targeted ticket can ever run the pipeline as designed.

**The evidence cuts both ways, which is why the halt is narrowed rather than removed.** During [[add-today-base-views-in-the-brain]] the clean-tree halt fired and was correct to: a `git add -A` at that moment would have swept live vault churn *plus roughly 180 iCloud conflict-copy files* into a single commit labelled with one ticket's name. The halt prevented a genuine disaster. So the lesson is not that the check is wrong — it is that the check and the staging are both scoped to the wrong thing. Scoped to the Coder's own paths, both recover their meaning: the halt still catches the case that actually endangers a build (someone else was editing the file I am about to change), and staging still produces a commit that contains one ticket's work and nothing else.

**The changed-file set is not new machinery.** The pipeline already snapshots the worktree before and after each Coder dispatch in order to review what was produced. This decision reuses that set as the staging list, so the commit's contents become a function of what the Coder actually did rather than of what happened to be lying around.

**Consequences.** A Brain-targeted commit no longer captures side effects the Coder caused indirectly — if a build triggers a dashboard regeneration, that file is not in the commit. That is the intended behaviour and it is also a real difference from how normal-repo builds behave, so the two paths now diverge and both need test coverage. The divergence is deliberate and narrow: one condition (`target_repo` is the Brain), two behaviours, asserted in tests rather than inferred.

**Rejected:** *drop the clean-tree check for Brain targets* — removes the protection that demonstrably worked, in exchange for nothing; *require the vault to be quiesced before a build* — the same unsatisfiable precondition wearing a manual ritual; *commit everything and sort it out in review* — makes the reviewer responsible for noticing 180 unrelated files, which is how they get waved through.
