# Protocol: Call Companion curation (v0)

Curation is a bounded, interactive planning flow in the Engine. It reads only *unclassified* active Tickets, defaults to at most twenty ordered by current priority, proposes `call_suitable` and `estimate_minutes`, and writes NO Ticket metadata until the user explicitly confirms. It is not a daily scan and creates no proposal database.

## Risk tier & Autonomy

- **Risk tier:** *internal & reversible*
- **Actor:** `EA`
- **Trigger:** `Call Companion curation`
- **Action type:** `ticket-planning-update`
- **Posture:** Confirm-first. No metadata write occurs without explicit user confirmation of proposals.

## Definitions

- **Ticket:** Markdown file under `tasks/projects/<slug>/` or `tasks/areas/<slug>/` with YAML frontmatter (per `protocols/ticket-normalization.md`).
- **Active:** `status` not `done` and not `deprioritized` (including status aliases `completed`, `closed`, `deprioritised`).
- **Unclassified:** `call_suitable` blank or absent. An explicit `false` or `true` is classified and must NOT be re-proposed.
- **Priority order:** `high` > `medium` > `low` > blank, then stable by path string ascending so runs are deterministic.
- **Planning metadata vocabulary:** Canonical forms per `protocols/ticket-normalization.md` (`call_suitable` boolean string `true`/`false`, `estimate_minutes` exact positive integer).

## Flow shape — three explicit stages

1. **Candidate Gathering (`gather_candidates(brain_path, limit=20)`)**
   - Read-only pass scanning `tasks/projects/<slug>/` and `tasks/areas/<slug>/`.
   - Files missing a valid YAML frontmatter block are not valid Tickets and are skipped during candidate gathering.
   - Filters for unclassified active tickets only.
   - Orders candidates by priority (`high` > `medium` > `low` > blank), then stable by path string ascending.
   - Enforces a hard cap of `limit` candidates (default: 20; `limit` must be a positive integer).

2. **Proposal Generation (`propose(candidates, provider)`)**
   - Accepts the candidate list and an injected callable `provider`.
   - `provider` is called exactly once with the list of candidates: `provider(candidates)`.
   - Validates that the provider returns a list, does not exceed candidate count, returns paths corresponding to gathered candidates, and contains no duplicate paths.
   - Each proposal carries:
     - `path`: relative ticket path
     - `call_suitable`: proposed boolean (`true`/`false`)
     - `estimate_minutes`: proposed positive integer
     - `rationale`: short rationale string
   - Proposals generated by `propose` do NOT carry confirmation markers.
   - Validates proposal fields (requiring exact positive integer for `estimate_minutes`) and raises on malformed values; writes nothing to disk.

3. **Confirmation & Writing (`apply_confirmed(brain_path, confirmed, now=None)`)**
   - Validates all proposals in a first pass before making any writes to ensure atomicity. If any proposal fails validation, no files or logs are modified.
   - Accepts only items carrying an explicit per-item confirmation marker (`confirmed: True`). Passing raw `propose()` output without confirmation markers raises a `ValueError`.
   - Resolves and validates candidate paths: requires each path to be inside `brain_path/tasks/` and to be one of the candidate paths returned by `gather_candidates`. Unsafe or unrecognised paths raise a `ValueError` naming the offending path.
   - Validates `call_suitable` and `estimate_minutes` (rejecting floats, zero, negative numbers, strings with leading zeros, or invalid booleans).
   - Reuses `frontmatter._update_frontmatter` to update YAML frontmatter for ONLY confirmed tickets.
   - Writes ONLY `call_suitable` and `estimate_minutes`. Never `status`, `planning_lane`, `planned_for`, or `critical`.
   - Preserves every other key, its order, list formatting, comments, and line endings (CRLF/LF).
   - Rejected and omitted tickets remain byte-identical.
   - Appends one Action Log record per confirmed ticket (`log_action.build_entry` + `append_entry`).
   - Returns a dict containing `applied` list of records (`[{"path": ..., "log_path": ...}]`) and `skipped` list of records (`[{"path": ..., "reason": ...}]`).

## Hard Constraints

- **Explicit confirmation required:** No write path is reachable without passing through `apply_confirmed` with an explicit list of confirmed proposals carrying `confirmed: True`. No "confirm all" default and no implicit confirmation derived from proposals.
- **Strictly scoped writes:** Only `call_suitable` and `estimate_minutes` may be written.
- **Path containment & candidate check:** Path traversal, absolute paths, non-candidate files, or paths with newlines are rejected loudly by raising `ValueError`.
- **Isolated execution:** Structurally incapable of Triage, Waiting For changes, or external actions (must not import `triage.py` or `execute.py`).

## Action Log Record

Each confirmed ticket update logs one entry to `log/YYYY-MM-DD.md`:
- `actor`: `EA`
- `trigger`: `Call Companion curation`
- `action type`: `ticket-planning-update`
- `input link`: ticket path string (e.g. `tasks/projects/goals-os/my-ticket.md`)
- `action`: description of updated planning metadata
- `confidence`: `High`

## Non-goals (v0)

- **No Brain-side changes:** Base view and action-type registration in `config/action-types.md` are a separate ticket (do not touch the Brain).
- **No proposal database or background state:** Curation is an on-demand, interactive flow, not a daily background scan.
